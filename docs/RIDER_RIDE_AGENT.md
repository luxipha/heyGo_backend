# Rider Ride Agent and live-trip contracts

Version 1, Nigerian Rider scope. The mounted app remains Agent-first. New backend cards reuse Rider tokens; existing map, Classic, chat, receipt and lifecycle widget layouts are preserved.

## Separate service

`services/ride-agent-gateway` is a separate HTTP process. Start it explicitly with `./scripts/dev.sh ride-agent-gateway`. Configure `PORT=8085` for local use and a generated server-only `RIDE_AGENT_INTERNAL_TOKEN` of at least 32 characters on both this service and api-gateway. Configure `RIDE_AGENT_URL` on api-gateway. The service uses neither the Rider database nor Rider session tokens. The local default four-service runner is unchanged. Terraform and the production release workflow now include the IAM-protected Ride Agent, its dedicated identity/secrets and candidate health check. Gateway uses `RIDE_AGENT_AUDIENCE` to add a Google ID token while preserving internal-token authentication. Its runtime has no database/Pub/Sub grants. Actual provisioning, Places-key configuration and cloud verification remain release gates.

`RIDE_AGENT_PLACES_KEY` enables the optional Google Places New adapter. An unset key returns unavailable, never fixture places. Nigeria region bias and bounding-box filtering do not establish service eligibility: approved market classification and pricing remain authoritative. `RIDE_AGENT_LLM_ENABLED=false` is the default. Optional private planner URL/token receive only the validated destination query and `search_places` allowlist, not user IDs, session tokens, finances, account details or live trip telemetry. Invalid tool/output/provider responses fail closed or use deterministic destination parsing. This service cannot create/cancel trips or access account/wallet/privacy/notification/Admin tools.

## Public read and confirmation

- `POST /rider/agent/resolve`: Rider role required; `{schemaVersion:1,message}` searches, `{schemaVersion:1,placeId}` resolves a selected stable ID. Optional `bias:{latitude,longitude}` is restricted to Nigerian bounds. Response contains `schemaVersion`, `state` (`resolved`, `clarification`, `unavailable`, `unsupported`), `candidates`, `place`, safe message, planner mode and `confirmationRequired:true`. Search/resolution alone never creates a trip.
- `POST /trip/preview`: mounted Rider sends schema version 1, resolved destination ID, optional resolved pickup ID and current device coordinates. Gateway re-resolves stable IDs, ignores supplied place coordinates as truth and persists confirmed metadata with the quote group. Backend OSRM geometry/distance/duration and approved market rates supply the preview. Version 1 maps protobuf coordinates into a GeoJSON `LineString` with `[longitude,latitude]` pairs; unversioned legacy geometry is unchanged. The controller validates and retains real geometry; the preserved old illustrative map is not used as authoritative route presentation.
- Preview options expose `fareKobo`, `noShowDebtKobo`, `amountDueKobo`, `currency:"NGN"`, `expiresAt`, `previewId` and backend fare ID. Version 1 removes `totalFareInPaise`; unversioned legacy clients retain that deprecated floating-point Kobo-valued alias. Legacy unversioned lifecycle events retain that alias for Driver compatibility and also expose canonical integer `fareKobo`/debt/amount-due and `currency:"NGN"`. There is no FX conversion or Paise interpretation. `previewId` groups independently consumable options for one route; it is not an idempotency key or dispatch promise.
- Option availability is explicitly `not_checked`, with null pickup ETA. A quoted price proves approved pricing only. Current safe assignment reads similarly expose null pickup ETA / `unavailable`; a numerical ETA requires a future authoritative provider.
- `POST /trip/start`: `{rideFareID,confirmed:true}` plus stable `Idempotency-Key`. Rider must explicitly review/confirm amount due. Existing clients must add `confirmed:true` and a stable key before rollout; the backend does not silently assume confirmation for legacy callers. Refresh/retry keeps the same key and fare ID. Expired/invalid/debt-changed quotes require a fresh preview and another confirmation; route edits discard selection immediately.
- `GET /rider/fares/:fareID/trip`: owned recovery read returns `{trip:null}` if unused, or the existing safe trip snapshot. Foreign/missing fares return 404. A persisted confirmed request can be recovered after restart without creating a trip.
- Cancellation commands require `{reason,confirmed:true}` when the caller is the trip's Rider, including dual-role identities. Driver command semantics remain available. Cancellation UI integration/acknowledgment belongs to J-13–J-15. Payment and account actions are excluded from Agent tools; no payment is automatically initiated by Agent text.

Malformed fare UUIDs return `400 invalid_fare_id`; unknown persisted fare IDs use `fare_invalid`. Stable public error reasons: `fare_invalid` (404), `fare_foreign` (403), `fare_expired` (410), `rider_restricted` (403), `debt_changed` (409), `market_unavailable` (409), `trip_service_unavailable` / route/place unavailability (503), `active_trip_exists` (409). Mutation failures are not presented as successful bookings.

Creation locks the Rider identity then the persisted fare, checks current debt, quote expiry and active-trip state, and commits fare consumption, trip/debt allocations and created-event outbox together. A consumed fare returns its original trip even after expiry. Deleted consumed trips fail closed. Migration 055 backfills the earliest original trip for already-used legacy fares; it does not remove historical duplicates. Debt changes serialize on Rider identity. Database deadlock/temporary failures remain retryable using the same request identity.

## Matching and streaming

`matchingDeadline` is persisted at creation (two minutes). No candidate or deadline expiry transitions pending/assigned trips to `cancelled`, with `matchingOutcome` (`no_drivers` / `timeout`), reason, timestamp/version and durable outbox event in one transaction. Offered reservations close and refresh availability. Offer expiry is capped by the trip deadline, and acceptance checks that deadline. Retry is a new Rider-confirmed request with fresh preview; a previously consumed fare recovers the old outcome. Pull workers scan every two seconds; push mode uses existing durable outbox delivery and Cloud Tasks offer-expiry handling. Release verification must exercise delayed/retried broker and task delivery.

`GET /rider/trips/active` reads the durable event tail **before** reading the snapshot and returns `afterEventId`. Connect `/ws/riders?afterEventId=evt_N` from that cursor; events between the reads/subscription are replayed. Duplicate snapshots/events are expected. No Rider cursor means `evt_0`; Driver compatibility retains its existing behavior. The app stores cursors per Rider, processes frames sequentially, refreshes owned snapshots for lifecycle events, suppresses old/duplicate IDs, and advances storage only after state application. Reconnect obtains a fresh snapshot and resumes from the older saved cursor. Stream failures preserve recovery controls rather than inventing lifecycle progress.

Safe snapshot/assignment payloads include assignment identity (`tripID:attempt`), vehicle make/model/color/plate/package, Driver public name/photo and nullable ETA. Pending/offered Driver details remain undisclosed. Arrival/start/completion/cancellation/rematching use backend state and never a local countdown.

Driver socket locations commit to the live-location row and Rider event store together under the current socket lease. Events contain trip/assignment/Driver identity, capture/receipt timestamps and 120-second freshness. Device `recordedAt` is used when supplied; otherwise `captureTimeSource:"server_received"` explicitly identifies the legacy receipt-time fallback. Future/stale/out-of-order readings and former socket/assignment updates are rejected. Read snapshots hide locations older than two minutes; matching eligibility independently retains its existing 30-minute predicate. The legacy Driver client must supply device capture timestamps before receipt-time readings can be called device capture proof.
