# Driver production readiness audit — 19 October 2026

Scope: standalone `/Users/abisoye/Projects/heyGo/apps/driver`; mounted entry `main.dart` → DriverController.bootstrap → DriverApp/SessionRouter. This supersedes Rider-specific conclusions for the Driver-first launch. Read-only audit: no app behavior, cloud configuration, credentials or deployment changed.

Verdict: not ready for general production launch. A signed internal Driver build can test Monnify Operating Balance top-ups without a Rider release once the prerequisites below are addressed.

## Findings in priority order

1. **Critical: CasperID login exchange is absent from the real router.** Driver `lib/services/api_client.dart:23` posts `/auth/casperid/exchange`. A synthetic, non-user request to the deployed endpoint returned HTTP 404. Backend `casperid_oauth.go` implements an exchange handler, but searches show it registered only in its isolated tests, not NewHTTPHandler/main. Deployment environment inspection showed no CasperID OAuth entries. Wire the real route and explicit server-only provider configuration, validate the registered client/redirect/PKCE contract, and observe sign-in, registration, restart and expiry against production. Do not substitute Rider OTP or enable development bypass.

2. **Critical: Maps configuration is missing in this release environment, and iOS deliberately crashes without it.** Driver AppDelegate supplies GoogleMaps with GMSApiKey; its release branch calls fatalError for an empty/unresolved key. Local Secrets.xcconfig exists but supplies no nonempty Maps key. Android has no key in the inherited environment or global Gradle property; it accepts an explicit Gradle project property as well, which must be supplied by the release workflow if used. The fresh iOS release artifact was inspected and its GMSApiKey is empty/unresolved, confirming the startup precondition fails in this build. Android artifact inspection remains open. Configure restricted native keys or agree an explicit supported launch behavior. The decision is broader than just enabling Rider Places; preserve the user's deferred provider/product decision.

3. **High: payment creation cannot safely recover an uncertain result.** Driver creates a new Idempotency-Key on every createOperatingTopup call and keeps the top-up reference only in the current dialog. A network loss/restart can lose the reference and create another checkout on retry. Gateway idempotency replays completed responses for a reused key, but removes reservations on 5xx. The gateway does not forward an idempotency identity to Payment; Payment creates a new top-up UUID/provider session on every invocation. A provider creation timeout leaves a pending database record without a recoverable client result. Persist a stable per-attempt identity, enforce it in Payment/database/provider initialization, and expose owned pending-attempt recovery/history. Test response loss, restart, concurrent replay and exactly-once financial posting. This is distinct from any existing webhook transaction deduplication.

4. **High: production build inputs and store release settings are unfinished.** Runtime defaults point HTTP/WS at the Android emulator and Origin at localhost. CasperID client ID defaults empty and validateAuthentication blocks sign-in without it. Supply reviewed HTTPS/WSS endpoints, allowed WS origin, provider/client/redirect settings, and enforce DEV_BYPASS_AUTH/DEV_SEED_TRIP/DEV_PLACEHOLDER_MAP=false for release. Development flags currently have no kReleaseMode guard. Android release signs with debug keys and targets SDK 34 (compileSdk 36); current Google Play new/update requirement is API 36. iOS has no DEVELOPMENT_TEAM project setting; external signing configuration remains possible but was not verified. Store policy source: https://developer.android.com/google/play/requirements/target-sdk.

5. **High for working drivers: background/location/recovery behavior is not established.** Source uses a normal foreground Geolocator position stream, no foreground-service notification configuration, no explicit app lifecycle resume recovery, no Android background/foreground-location service configuration, and no iOS location background mode. There is no FCM/APNs client dependency/bridge for offline offer delivery. Sockets reconnect while the process is executing; that does not prove delivery while locked/suspended. Define the supported working-driver background behavior and verify device lock, app switching, navigation, network interruption, restart and authoritative active-trip/availability recovery.

6. **Medium: Finance reads may appear as zero or stale data.** refreshDriverAccountData waits for earnings, balance, transactions, performance, reviews and safety contact as a single Future.wait, discarding all results when any one fails and retaining prior maps. Earnings and Wallet activity default missing financial values to zero and empty transaction lists to 'No ... transactions yet'. Separate relevant read outcomes and render unavailable/stale states with explicit retry before making money/availability decisions. Top-up limits default to zero, which can block all valid amounts when balance reads fail.

7. **Medium: browser-return recovery is manual and transient.** Operating top-up status refresh is available inside the current dialog; checkout opens externally. No payment-specific native return link or app-resume refresh exists, and the return page asks the user to manually reopen HeyGo. Persist pending references and provide a durable resume/check-status path. Browser return must never mark payment successful. The current checkout launcher also accepts any nonempty backend URL; validate HTTPS and reject malformed/user-info URLs at the boundary.

8. **Remaining operational/provider gates.** Verify approved Driver onboarding documents/inspection/manual review, actual location in an active market, approved Operating Balance policy/minimum/top-up bounds, private uploads, real CasperID verification, native maps/routes, full offer→accept→arrival→start→complete→direct-settlement journey, Support/SOS handling, token expiry/re-login, background behavior and Monnify notifications. A real recent location (within 30 minutes) and account email are required by the top-up backend; only goOnline/reconnect currently transmit location, so validate the first-funding path before assuming Add Money works on a newly approved account. No authenticated real Driver account was used in this audit.

## Payment test path

Driver Earnings → Add Money starts a Monnify Operating Balance top-up. It is separate from direct Rider fare settlement. Rider app rollout is not a prerequisite.

After fixing login, build/native configuration and durable payment recovery: use a controlled eligible Driver with a valid email, recent in-market location and approved market top-up policy. Submit one sandbox top-up within limits, complete checkout, verify provider webhook delivery, authoritative top-up status and balance/ledger credit, replay notification and original create identity, and confirm exactly one credit. Do not use live-money Monnify credentials or bypass eligibility/market controls for convenience.
